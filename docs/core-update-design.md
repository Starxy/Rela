# Core 版本与事务切换

此文约束 T33–T34。Windows 服务、UAC 和真实 TUN 验收仍必须在独立测试机完成。

## 版本来源

- 随包版本：通过嵌入的完整文件摘要校验后读取固定 Core 版本。
- 已部署版本：管理员成功部署后写入受保护的部署记录；GUI 通过 SCM 的只读描述元数据读取其公开版本副本。没有记录时显示未知，不用随包版本代替。
- 运行版本：SCM 确认专用服务运行、程序路径属于 Rela 后，从实际 node RPC 的 version 字段读取，并核对固定 instance_id。
- 引擎修订：config/easytier-version.json 中单调递增的 engine_revision，避免把开发版提交哈希按字典序当作版本先后。相同修订不得对应不同版本或文件摘要。
- 部署所属 Rela 版本：阻止低版本副本重写高版本副本的引擎或运行配置；断开和读取不受此限制。

## 历史客户端隔离

旧实现始终覆盖 ProgramData/Rela/engine。新实现迁移到 engine-v2，并通过官方 CLI 更新已核对的固定服务路径与工作目录。历史客户端的服务路径检查会拒绝操作新位置，防止没有版本守卫的旧程序降级服务。只接受 engine 与 engine-v2 两个精确的服务程序路径，不接受任意程序或参数。

## 切换事务

1. 持有机器服务控制锁，恢复未完成事务，再校验请求、随包资产和已有部署版本。
2. 在受保护目录准备完整引擎、部署记录和新 TOML；此时保留现有连接。
3. 原子写入事务日志，记录此前服务是否存在/运行、原路径、文件存在性、旧配置能否安全重启。
4. 停止服务并等待退出；把原引擎和 TOML 移到事务备份，将暂存内容移到固定新位置。
5. 通过官方 CLI 安装或切换专用服务路径和工作目录，启动并验证服务状态、RPC 实例和实际版本。
6. 验证通过后发布公开版本信息并写提交标记，再清理事务备份。网络连接仍由真实节点与 TUN 状态判定。
7. 失败或重启后发现未提交日志时，停止新服务、恢复原文件和服务路径；仅当旧配置使用 credential 时允许恢复此前运行状态。旧主密码配置不自动启动或回退认证。

所有路径由程序生成，拒绝重解析点与意外目录内容；日志不含 credential，备份 TOML 保持管理员/系统 ACL。取消 UAC 前不会发生服务切换。恢复失败时保留日志和备份，报告需要恢复，不继续覆盖。

## 随本体更新的延迟提交

本体更新使用单独的应用事务编号，复用已生效的受保护 TOML，不应用 GUI 中尚未重连的设置。准备后保留旧文件，停留在 AwaitingApplication；普通连接流程不能消费这笔事务。原服务停止时保持停止，未安装服务时不自动安装。协调者收到新本体启动确认并持久化提交决定后，再要求 Core 提交；提交前失败则同时回退本体和 Core。

受保护的完成回执记录事务编号和最终决定，允许重试相同决定，拒绝提交后改成回退。助手丢失连接不自动选择回退，以免与已持久化的本体提交决定冲突。提交时再次核对实际引擎、配置摘要和运行 RPC。详见[本体更新与恢复事务](update-recovery-design.md)。参与者接口、受限提权助手和绿色版协调已接入；实际 UAC、SCM 与真实断网升级验收仍待独立机器。

## 验证

文件事务与故障注入测试覆盖准备、备份、替换、启动、提交和清理边界，并保留原配置字节；版本测试覆盖旧副本、同修订内容变化和未知版本。它们仅证明算法与文件行为，不能代替独立 Windows 服务/TUN、UAC 取消和真实两版本升级验收。

2026-09-29 实现状态：已接入连接、重连和断开流程；协议 v8 和设置页分开展示三种版本。15 项文件事务测试覆盖首次安装、原位更新、旧目录迁移、各步骤错误与模拟进程终止、恢复重试、提交后文件占用、旧副本、篡改拒绝以及本体更新的延迟提交与回执；Windows 参数解析测试验证固定路径与完整参数。真实隔离 Core 的 node.version 与随包版本一致，未创建服务或 TUN。权限、SCM 切换、UAC 和真实断网恢复仍未验收。
